# 物理不变量宪法

> **一句话：本仓不接受"看起来对"的物理。**
> 任何改动只要让下面任一条不变量失效，就是**物理 bug**，不是"参数需要调"。
>
> 这份文档把散落在 40 多个测试文件里的防线汇总成一张表，并写清"改代码时必须遵守什么"。
> 它**不是**愿望清单——每条判据都指向仓内真实存在、CI 里真的在跑的测试或门禁。

## 1. 什么算物理 bug（五类）

| # | 类别 | 症状 | 为什么危险 |
|---|---|---|---|
| 1 | **发散** | 迭代过程中冲量/速度单调增长，几 tick 内炸到 `inf`/`NaN` | 静默污染整场；`Distance` 关节的符号 bug 就是这个（`v·n` 序列 `0 → −7.2 → −21.6 → … → −914`） |
| 2 | **穿透** | 动态体穿过静态体或互相重叠超过 `slop` | 视觉上是"物体消失"，根因常是 CCD 缺失或窄相漏解 |
| 3 | **能量注入** | 无外力场景下总机械能增长 | 静止物体会自己抖起来；这是 Baumgarte 偏置与 iteration 交互的经典坑 |
| 4 | **非确定性** | 同一配置跑两次结果不同，或跨平台不同 | 无法回放、无法复现 bug、无法做回归——**这是最贵的 bug** |
| 5 | **静默失效** | 约束/门禁"跑过了"但什么也没做 | `gate_gold.sh` 第一版就踩过：场景名被 `shift` 掉，三个场景全跑错而退出码全 0 |

## 2. 判据与现有防线

### 2.1 发散

**判据**：任何量在迭代过程中**单调增长且无界**。最小探针：在求解器里打印迭代轨迹
（`len / bias / v·n / k / lambda`），看它是**收敛序列**还是**等比放大**。

**现有防线**：
- `crates/vxl-phys/tests/joint_break.rs` — 关节在给定力下必须断开、不断开时约束仍生效
- `crates/vxl-phys/tests/default_tier_stability.rs` — 默认档 3000 步长跑，冻结末态读数
- `crates/vxl-phys/tests/ccd_energy.rs` — CCD 命中后的速度/能量行为

> **教训（2026-10-17，提交 `922e685`）**：`Distance` 关节的 `lambda = -(v·n + bias)/k` 在
> `apply_pair` 的约定下解出 `v·n = +bias`，与收敛目标 `v·n = −bias` **符号相反** ⇒ 每轮
> 冲量翻倍。**排查方法**：先写最小探针确认缺陷真实存在 → 插 `eprintln!` 打印迭代过程 →
> 用 `Select-String` 验证打印真的插进去了 → 看到 `v·n` 每次翻倍即锁定"迭代发散"而非"偏置太大"。
> **没有中间状态就无法区分「参数不合理」和「公式错」。**

### 2.2 穿透

**判据**：稳态下动态体埋入静态体的深度 ≤ `config.slop`；穿透不得随 tick 增长。

**现有防线**：
- `crates/vxl-phys/tests/deep_penetration.rs` — 初始深穿透的恢复
- `crates/vxl-phys/tests/ccd_thin_shell.rs` — 薄壳不被高速穿过
- 金样里的「超 slop 点」计数（`scripts/gate_gold.sh` 的 `tower25` 档）

### 2.3 能量注入

**判据**：**有阻尼/摩擦**时总机械能只减不增；**无外力**时动量守恒。
注意：Baumgarte 去穿透偏置**会**注入能量，所以判据必须写成"能量不增"而非"守恒"，
且必须在**稳态**（已沉降）后采样，不能在投放瞬间。

**现有防线**：
- `crates/vxl-phys/tests/ccd_energy.rs`
- `crates/vxl-phys-fluid/src/tests/hydrostatics.rs` — 静水压解析对照
- `crates/vxl-phys-splat` 的动量账（`bridge_state_ledger.rs`）

### 2.4 非确定性

**判据**：同配置同机**逐位相同**；跨平台差异必须**有界且已知**。

**现有防线**：
- `crates/vxl-phys/examples/determinism.rs` — 两次运行逐位比对
- `crates/vxl-phys-fluid/src/tests/determinism.rs`
- CI 的「确定性（Clang / GCC / MSVC / GCC-aarch64-qemu）」四个 job
- CI 的「跨平台哈希比对」job
- `crates/vxl-phys/tests/determinism_flag_inert.rs` — 开关不影响结果

> **硬规矩（2026-10-17 实测）**：数值路径上出现 `sin/cos/atan/exp` ⇒ 走 libm ⇒
> Windows（UCRT）与 Linux（glibc）有 ulp 级差异，接触驱动的混沌系统会把它放大。
> **金样场景的设计必须自问：这条路径里有超越函数吗？**
> 但**去掉三角函数也不够**——`m6_wheeled_car` 改成纯 `±×÷/sqrt` 后，跨平台仍差 `1.2e-4`。
> ⇒ 判据强的场景用位模式（收敛型：浮体、布、绳索）；接触驱动的多体系统用**有界容差**，
> 并在文件头写清为什么不能要求位模式。

### 2.5 静默失效

**判据**：门禁必须能证明它**真的做了判定**。

**现有防线**：
- `scripts/gate_gold.sh` 的 `run_scene` — 检查输出里必有「金样基线 PASS」，
  出现「跳过基线判定」即失败
- `crates/vxl-phys/tests/default_tier_stability.rs` 的 `gate_is_sensitive_to_sweep_reduction`
  — **门的金丝雀**：把扫掠降到地板以下，读数必须明显不同，否则说明场景选得不够灵敏
- `crates/vxl-phys/tests/xpbd_solver_gate.rs` — 未立项的架构不得悄悄接线

## 3. 改代码时必须遵守什么

### 3.1 改动求解器核心

1. **先证明缺陷存在**：写最小探针，不要凭代码阅读下结论。
2. **插打印看轨迹**：收敛 vs 发散，只有轨迹能区分。
3. **改完必须重跑**：`cargo fmt --check` → `god_gate.py` → `args_gate.py` →
   `cargo clippy --workspace --all-targets -- -D warnings` → 全量测试 → `local_gate.py`。
   **"跑过门禁"指的是跑在最终版本上**——改完字面量不复跑 clippy，等于没跑
   （`excessive_precision` 一次打掉过五个 job）。
4. **改了 `Distance` / 关节 / 接触**⇒ 必须重跑 `bash scripts/gate_gold.sh`，
   三档金样全过才算完。

### 3.2 改金样

1. **基线只用 `f32::from_bits()` 写**。十进制字面量超过 7 位有效数字会触发
   `clippy::excessive_precision`（默认 lint，`-D warnings` 下就是错误）。
2. **每次改基线数字，旁边必须写动因**。只改数字不写原因，半年后没人能判断那是修复还是回归。
   反例：`m6_float_mooring` 的 `vy_held` 从 `0x35c0_b434` → `0xb5bf_4bca`（只翻符号），
   当时没写说明，后来复核时差点被当成新缺陷。
3. **绝不用 `--write-baseline` / `--write` 放宽棘轮**。要放宽必须走 10% 交换窗，
   且 `max_fn_lines` 必须严格下降。

### 3.3 改门禁脚本

1. **多行输出必须主动压成单行**。GitHub Actions 会把多行 echo 合并成一行，
   金样失败的「期望 / 实测」两行就是这样被吃掉的（已修：`sed -e :a -e 'N;s/\n/ ⏎ /;ta'`）。
2. **失败退出前先打诊断**，不要被 `set -e` 吃掉输出。
3. **逐项贴退出码**，管道会吞掉真实的 exit code。

### 3.4 环境

1. 所有命令必须显式带 `RUSTUP_HOME` / `CARGO_HOME`，否则 `cargo` 报
   `rustup could not choose a version`，而 `$LASTEXITCODE` 可能仍然让后续步骤"看似"跑过。
2. 门禁脚本一律 `python -X utf8` + `PYTHONUTF8=1`。
3. 含 markdown 反引号的长文本走 python 写——PowerShell 双引号里的反引号是转义符，
   `` `0 `` 会写进 **NUL 字节**。

## 4. 前瞻方向的取舍（哪些不做）

上一轮的设计评审（`UNIFIED-SOLVER-REVIEW.md`）和前沿调研得出三条硬边界：

### 4.1 不做统一求解器

2.4 万行核心、9 项金样全变、FLIP 根本纳不进来（算子分裂没有残量概念）、
顺序敏感度还会上升。**架构上的正确，工程上的亏本。**

### 4.2 不用神经网络做物理代理

看起来符合「既要又要」，但它**天生违反第 2.3 与 2.4 条**：能量不守恒、无法逐位回放。
和"不允许物理 bug"直接冲突。可以用于**场景生成/参数搜索**，不能进求解环。

### 4.3 GPU 只做纯函数，不做求解器

宽相、窄相、流体这类**无状态纯函数**可以上 GPU（`vxl-phys-gpu` 的 FLIP 已经跑通）。
求解器**不**上 GPU：一旦出现数值问题，没有稳定的逐位回放，调试成本是灾难性的。

### 4.4 值得做的方向（按收益排序）

| 优先级 | 方向 | 为什么四条同时变好 |
|---|---|---|
| 1 | **VBD 块坐标下降**用于布料↔刚体、绳索↔刚体两条边 | 块下降**结构上单调**（不会发散）、**顺序无关**（消除 `+0.098 / −0.124` 那种偏差）、块间可并行（复用现有岛级并行）、新约束只需实现一个接口 |
| 2 | 把**逐位确定性**做成产品（回放/差分调试/场景即基线） | 不碰物理核心；别的引擎没有这个能力 |
| 3 | GPU 纯函数下沉 | 复用已跑通的 FLIP 路径 |

**核心判断**：块坐标下降本身就是一个「既要又要」的数学结构，Gauss-Seidel 不是。
追这个是**改数学**，不是改架构——风险可控，金样影响面只在那两条边上。

## 5. 这份文档的执行方式

- 新增任何物理域/求解器 ⇒ 必须先在本文档里回答：它守上面哪几条？判据是什么？
- 发现新的物理 bug ⇒ **修完之后在这里加一条**（症状 / 根因 / 判据 / 防它的测试）。
  本文档是**活的**，不是一次性的宣言。
- CI 里没有对应门的判据 ⇒ 记为**缺口**，不要假装它被守住了。
