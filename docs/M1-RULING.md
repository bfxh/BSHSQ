# M1 刚体核心 · 性能档裁决（核口径）

> 出口判据（`ROUTE.md §7`）：**稳定 ✓ + 金样容差 ✓ + 性能档（SPEC §3）或核口径裁决**。
> 本文给出本机测得的成本结构，并回答"不走改写架构能不能达标"。

## 1. 本机实测（2026-10-30，`m1_pile` 10k 体、600 tick、单线程、release）

| 配方（iters / substeps） | 累计均值 ms/tick | 末态深穿透体 | 最大深度 |
|---|---|---|---|
| **16 / 1**（现行默认） | **72.8 – 81.9** | 4 – 75 | **0.714** |
| 16 / 4 | 353.9 – 406.6 | **0 – 10** | **0.008** |

两件事同时成立：

1. **子步把穿透压掉两个数量级**（0.714 → 0.008）——这正是 `DESIGN-staged-solver §7 缺陷①`
   说的"子步每遍 ≈ inner 的 4 倍价值"；
2. **但它贵 4.9×**（不是文档里 8B 场景的 1.84×，因为 10k 堆的接触更密）——因为
   `World::step` 每个子步都重跑宽相/窄相（缺陷②）。

⇒ **性能档的缺口不是解算器的算术量，是"每子步重跑碰撞检测"的固定成本。**

## 2. 三条已试过的路（都不通，别再走）

| 路 | 实测结论 | 出处 |
|---|---|---|
| 直接打开 `detect_once_per_tick()` | 金样 pile5 红 + **更慢 +29%**（保真退化让堆一直醒） | `impact.rs:34-42` |
| 准静态门（`max|v|·dt ≤ 0.5·skin`） | 门内复用会丢"深度/锚点按当前位姿重算"的细化 ⇒ 不可靠 | 同上 |
| (4,16,1) 便宜子步 | 2 个实锤：解算 −1/4，但**窄相 ×4 盖过收益** | `DESIGN-staged-solver §7 缺陷②` |

### 2026-10-30 追加：接触集**签名门**（试过，比旧门好，但**不优于现行默认**）

门从"速度阈值"换成"**连续两 tick 的接触集签名相同**（体对 + 点数 + 量化到 1e-4 的深度）+ 宽松速度兜底"。
签名是纯函数（顺序无关 / 方向无关 / 深度敏感 / 吸收 1e-5 抖动，4 条测试）。

| 场景 | 基线 | 签名门 | 判定 |
|---|---|---|---|
| col45 | — | 全过 | ✅ |
| **pile5** | 横向 0.0018 | **0.0012（−33%）** | 更好 |
| **tower25** | 横向 0.0165 | **0.0249（+51%）** | **更差**（仍在物理判据 ≤0.0260 内） |

入睡 / 超阈 / deep / Δpos **全部不变**，只有横向这一项、且两场景**方向相反**。

⇒ **裁决：不换代。** 拿 25 层塔的 51% 横向保真换 2000 体的 33% 收益不划算；
只重录 pile5 而让 tower25 一起变成 +51% 的记录，等于把退化静默改成"通过"。
⇒ 签名门**严格优于旧速度门**（旧门双输：入睡 1994/2000 + 慢 29%），但**不优于现行默认**。
真出路仍是下面 §3 的 ②/③（speculative contacts / 子步只重烘焙深度锚点）。

## 3. 裁决

**在"每子步重跑碰撞检测"这个架构下，性能档不可达，且与稳定性直接对冲**：
- 要稳定性 ⇒ 上子步 ⇒ 付 5× 检测成本；
- 要速度 ⇒ 单子步 ⇒ 最大深度 0.714（穿过 0.25 m 盒半厚的 ~3 倍）。

⇒ **M1 的性能档出口 = 改写"检测一 tick 一次、子步只重烘焙"这条管线**，三选一：
1. 门换成**接触集签名不变**（集合与几何都稳定才复用）；
2. **speculative contacts**（按一 tick 最大推进预生成接触，允许预测穿透）；
3. **子步只重烘焙深度/锚点**（几何复用、数值细化）。

任一落地前，**M1 按"稳定 ✓ + 金样 ✓ + 性能档未达（有裁决）"收口**，不冒充满分。

## 3.5 实测：tick 内**新接触点**比例（只读探针）

"复用接触集"唯一丢掉的是**tick 内新出现的接触点**（深度/锚点每子步都会按当前位姿重算）。
只读探针 `vxl_phys::world_step::contact_probe`（线程内、关闭时每子步只多一次原子读）：

| 场景 | 规模 | 新增点 / 观测点 | **比例** | 最差单 tick |
|---|---|---|---|---|
| tower25（25 层单柱） | 25 体 | 6,857 / 34,735 | **19.74%** | 22.50%（tick 43） |
| pile5（5 层 × 20²） | 2,000 体 | 1,224,984 / 7,662,759 | **15.99%** | 22.79%（tick 9） |
| 12 层塔（参照） | 12 体 | 3,796 / 17,241 | 22.02% | 23.15% |

复算：`cargo run --release -p vxl-phys --example contact_churn -- tower 25 120`（或 `pile 5 20 120`）。

**判读**：两个金样场景的 tick 内新点比例都在 **16–20%**，属常态 ⇒ 冻结接触集的代价与"新点比例"
成正比，`predict_dt` 调系数补不上（它只能把**已知**点看远，预测不了"会出现哪些新特征"）。
与签名门实测吻合：pile5（重复接触多）−33%、tower25（逐层新建接触）**+51%**。

⇒ 当时据此判"下一步只剩 swept speculative 候选生成"。**该判读已被 §3.6 的实测否证**
（漏掉的点几乎都不是"宽相没给候选对"，而是同一体对上的特征切换）。

## 3.6 实测：速度预测覆盖不了 churn（反事实探针，2026-10-31）

§3.5 只量"冻结接触集会丢多少新点"，没量**速度预测视野**（`set_predict_dt`：接受带从
`sep ≤ skin` 放宽为 `sep ≤ skin + max(0, 接近速度)·dt`）能把它们补回来多少。
做法：tick 首子步在**同一批候选对、同一速度、与真窄相同点（解算前）**再跑一趟
`predict_dt = 整 tick` 的窄相，结果**不喂解算器** ⇒ 动力学与不开探针逐位相同；
再与后续子步的真实流形比对。

复算：`cargo run --release -p vxl-phys --example contact_churn -- tower 25 120 --predict`
（`pile 5 20 120 --predict` 同理）。

### 3.6.1 预测覆盖率

| 场景 | 后续子步实点 | 首子步没有的新点 | **新点被预测覆盖** | 漏因：同对换特征 / 窄相视野拒收 / **宽相无候选** |
|---|---|---|---|---|
| tower25 | 34,735 | 10,300 | **1（0.01%）** | 10,243 / 56 / **0** |
| pile5 | 7,662,545 | 1,951,222 | **43,429（2.23%）** | 1,803,377 / 104,360 / **56** |

整份预测集里**投机点只有 2 / 51,589 个（0.0% / 2.0%）**：这两组场景里"按接近速度把接受带
放大一整 tick"几乎不产生新接触——体对要么不接近，要么早就接触了。

### 3.6.2 新点按位置再分（半径 = `max(2·skin, 1cm)`，即窄相点去重阈值）

| 场景 | 同体对·同位置换 ID | 同体对·真新位置 | 新体对 |
|---|---|---|---|
| tower25 | 6,705（65.1%） | 3,539（34.4%） | 56 |
| pile5 | 1,446,773（74.1%） | 399,236（20.5%） | 105,327 |

⇒ 按观测点算，冻结接触集**几何上真正丢掉**的是 **10.4%（tower25）/ 6.6%（pile5）**；
其余是同一位置上的特征 ID 翻转（旧点还在，深度/锚点按当前位姿重算 ⇒ 几何不丢，
丢的是 warm-start 的 ID 匹配）。

### 3.6.3 判读（撤回 §3.5 的"swept 候选对"结论）

1. **速度预测只覆盖新点的 0.01% / 2.23%** ⇒ 调 `predict_dt` 补回冻结接触集，不成立。
2. **宽相无候选对只有 0 / 56 条** ⇒ 扫掠宽相也补不上：体对早就在候选表里（fat 边距本来就是
   `|v|·dt·6`）。§3.5 的"只剩 swept speculative"**在本机读数上站不住**。
3. 主因是**特征切换**：65–74% 的新点是同体对、同位置、换了 feature ID；另有 20–34% 是同一体对
   上的真新位置。后者来自"窄相在该时刻还没接受这个特征"，扫掠体对解决不了。
4. ⇒ 下一步按性价比排序（先量再改）：
   a. **特征 ID 稳定性**：同一几何位置跨子步保持同一 feature ⇒ 冻结集的 warm start 才可能命中；
      这条对**现行默认档**（每子步重检测）也有独立价值，不依赖 M1 复用。
      **（§3.7 已按实测降级：回退分支本来就暖启动，ID 稳定化最多把 6–7% 的回退升级为精确。）**
   b. 每子步重烘焙详情（现行做法，不动）。
   c. swept 候选生成只在"新体对"上有限（tower 0.5% / pile 5.4%，且多数已在候选表里）⇒ 优先级最低。

⚠️ 口径边界：`predict_inflate` 只用**质心相对速度在法向的投影**（不含角速度，也不含切向运动
导致的换特征）⇒ "特征切换补不上"是**该实现的结论**，不是"任何预测都不可能"。

## 3.7 实测：warm「未匹配」是哪道门拒的（2026-10-31）

§3.6 之后的第一候选是"特征 ID 稳定性"。求解器本来就有跨帧匹配计数（`warm_match_stats_take`，
`EXPERIMENTS §K.1` 用过）：塔上 69.6% 精确 / 18.7% 回退 / 11.7% 未匹配；**回退那半已按位域拆过**
（78% 是"面选择变了"），**未匹配那半一直没有成因读数**。本轮补上：把回退分支的三道门做成**互斥**
归因（只计数、不改行为），读口 `vxl_phys_solver::warm_match::miss_gate_take()`。

| 场景（substeps=4、120 tick） | 精确 | 回退 | 未匹配 | 未匹配拒因：深度门 / 距离门 / 深度跳变门 |
|---|---|---|---|---|
| tower25 | 72.7% | 6.1% | 21.1% | 233（2.4%）/ **5,641（57.8%）** / 3,880（39.8%） |
| pile5 | 80.1% | 7.0% | 12.9% | **1,074,496（82.3%）** / 164,400（12.6%） / 66,207（5.1%） |

自校验：三桶之和 **精确等于**未匹配数（两场景都是；口径不一致会直接红）。

**判读**：

1. **塔的未匹配主因是距离门**（1×skin 内没有上一帧锚点 ⇒ 材料点真的换了位置/换了一组点），
   与 §3.6 的"同对真新位置 34.4%"同源。**放宽半径不是解法**——历史实测：放宽到 4×skin 会错配
   锚点 ⇒ 暖冲量过驱动 ⇒ 堆族永不入睡（`match_warm_point` 注）。
2. **堆的未匹配主因是深度门**（本帧 `depth ≤ 0`：已分离/投机接触不继承暖冲量）⇒ 这是**设计上的
   拒绝**，不是缺陷。
3. ⚠️ **"特征 ID 稳定化"因此降级**：回退分支**也暖启动**（只是锚点取近邻）⇒ ID 稳定化**不会**把
   任何"未匹配"变成命中，最多把 6–7% 的回退**升级为精确**；而未匹配的 21% / 12.9% 一分不动。
   ⇒ §3.6.3 的候选 a 上限很小，不足以支撑 M1 的性能档。
4. ⇒ 剩下的杠杆回到"**让检测本身更便宜**"（卡上窄相档 / SIMD）或"**接受 4 子步成本改核口径**"，
   两者都不是本轮读数能裁决的，需要单独立项 + A/B。

复算：`cargo run --release -p vxl-phys --example contact_churn -- tower 25 120`（末尾两行 `[warm]`）。

## 3.8 成本结构：4 子步里**求解占 83%**、检测只有 16%（"让检测更便宜"的天花板）

§3.6/§3.7 关掉了三条"少检测"的路（冻结复用 / 速度预测 / 特征 ID 稳定化）。剩下的假设 A 是
"**让检测本身更便宜**"。先量结构（工具只读，每档两遍顺序交错；引擎侧 `World::timings()`，ms/tick）：

```bash

```

|---|---|---|---|---|---|
| substeps=1 | **38–39** | 5.0–5.5（13–14%） | 3.2–3.5（9%） | 27–28（71–72%） | 8.5（22%；另有 ccd 2.1） |
| substeps=4 | **151–153** | 15.7–15.9（10.5%） | 13.4–13.6（8.9%） | **120–121（80%）** | 29.5（19.5%） |

（本节以下绝对值均为**凉机同段交错**读数。）

2. 真正的瓶颈是**求解**：密集堆在 4 子步下几乎连成单岛 ⇒ 岛级并行拿不到；且求解量随子步
   **线性**涨（3 sweeps → 12 sweeps/帧）。
3. ⇒ 下一步该量的是"**求解内部**"（§3.11：构建 54–69%）与"**求解能不能并行**"
   （岛内切分 / 图着色 / 接触级并行），而不是检测。

## 3.9 实测：sweep 预算 12 → 8（以及真正的拐点在哪）

**开销**（`substep_cost m1pile 120 <iters> 4 8`，10k 体、8 线程，检测量不变；凉机同段交错）：

| sweeps（iters×inner×substeps） | wall ms/tick | solve |
|---|---|---|
| 12（3×1×4） | 151–153 | 120–121 |
| **8（2×1×4）** | **132（−13%）** | **101（−16%）** |

🔴 **更正（2026-10-31 晚）**：本表初版记的是 12 = 193–200 → 8 = 131–132（**−32%**）。那是**热机**
读数（此前连跑 600 tick 大场景）；凉机同段交错复测为 **151–153 → 132（−13%）**。理由见 §3.11：
sweeps 只动迭代那一段，而迭代只占 solve 的 39% ⇒ 理论收益 ≈ 0.39×(1/3) ≈ 13%，与复测吻合。
**"省 32%" 作废。**

**质量**（金样 `pile5` 2000 体、600 tick、Rapier 对照；`inner=1`、`substeps=4`，改 iters）：

| sweeps | 最强穿透 | Δpos max | 超阈点 | vxl/rapier 活跃期代价 |
|---|---|---|---|---|
| 8 | 0.0147 | 0.0322 | 4,653 | 2.58× |
| 12 | 0.0083 | 0.0223 | 4,134 | 2.44× |
| **16** | 0.0075 | 0.0175 | **54** | **1.16×** |
| **32** | **0.0000** | 0.0060 | **0** | **1.31×** |
| 64 | 0.0000 | 0.0046 | 0 | 2.84× |

`linear_slop` 0.005**。**该问题本身的前提要改**：12 已经在悬崖下，不是"再减一点"。

**拐点**：16 sweeps 起超阈点从 4,134 掉到 54，32 sweeps 完全干净（穿透 0、超阈 0）且**相对代价最低**
（1.31× Rapier）；64/256 只是把同样的干净再买贵一倍/五倍。⚠️ 注意 8/12 的"相对代价"反而比 16 **更高**

## 3.10 实测：往 12 以下压——只有"换子步"这条路，且不省时间

§3.9 的 12 sweeps = 4 子步 × 3 迭代。往下压有两条路：**减迭代**或**加子步换减迭代**。
同一场景按"分割方式"扫（金样 `pile5` 2000 体 / 600 tick / skin 0.01 / inner=1）：

|---|---|---|---|---|
| 4 × 1 | 4 | 0.0264 | 4,850 | 0.0395 |
| **4 × 2** | 8 | 0.0147 | 4,653 | 0.0322 |
| 3 × 3 | 9 | 0.0124 | 5,734 | 0.0267 |
| 2 × 4 | 8 | 0.0210 | 4,769 | 0.0329 |

3. **减迭代省的钱很薄**：4×2 只 −14%（132 ms），且加回子步换稳定后（6×2）反而 +37%。
4. ⇒ 若目标是"省时间"：**12 以下没有免费点**，4×3 就是前沿最便宜的一端；
   若目标是"更稳"：7×1 可以买到 0.0114 的深度，代价 +44%。
5. ⚠️ 上一版判读里的 +8%/+31%/+53% 是热机读数；凉机同段为 **+37%/+44%/+72%**，
   方向不变但幅度更大（热机对大子步配置的惩罚被放大）。

## 3.11 实测：求解内部三段——**约束构建占 54–69%**，迭代只有 22–39%

`ISLAND_SEG_PROBE`（`cfg.rs`，默认 `false`）打开后 `IslandDiag.build/warm/iter` 才有值。
本机探针开销可忽略（本场景只有 1 个岛；开/关同段 147.7–155.7 vs 148.4–151.7）。10k 体、8 线程、
120 tick、探针开（`substep_cost` 的 `solve内` 三列）：

| 配置 | solve ms/tick | 约束构建 | 热启动 | 迭代 |
|---|---|---|---|---|
| 4×3（12 sweeps） | 117.9 | **53.7%** | 6.9% | 39.4% |
| 6×2（12 sweeps） | 163.4 | **56.0%** | 8.7% | 35.3% |
| 8×1（8 sweeps） | 203.2 | **68.6%** | 9.3% | 22.1% |

**判读**：

1. **约束构建是求解的大头**（每子步 × 每接触点重建）；迭代扫掠只占 22–39%，随 sweeps 减少而
   占比下降（8×1 时只剩 22%）。
2. 这解释了 §3.9 的更正为什么是 −13% 而不是 −32%：sweeps 只动迭代那 39%，理论收益
   `0.39 × (1/3) ≈ 13%`，与凉机实测吻合。
3. 也解释了 §3.10 的"加子步赔钱"：加子步会把**构建 + 热启动**（约 63%）按子步数再乘一遍，
   而这一块不随 sweeps 减少。
4. ⇒ 真正的优化目标是**约束构建**（或安全地跨子步复用——`DESIGN-staged-solver §10` 试过
   "复用约束 + prepare" 并崩，要重开必须先补判据），以及**岛内并行**（§3.8：主岛占 99.7%）。

## 3.12 实测：约束构建内部——预处理 ~40% / 点循环 ~60%

§3.11 定位到"构建占 solve 的 54–69%"。再往下拆一层：`vxl_phys_solver::build_seg` 在
`build_island_constraints` 里对**整次 `build_constraint` 调用**计时，`build_constraint` 内再用一个
RAII 计时器量**点循环**；预处理 = 两者之差。抽样 1/16 流形（`m.a.is_multiple_of(16)`，确定性），
只对样本流形读钟 ⇒ 探针开销可忽略（开/关同段 199 vs ~150 ms）。

| 段 | 4×3 | 8×1 |
|---|---|---|
| **预处理**：函数入口 / 材质对 / warm 槽 `HashMap` 查找 / 摩擦基 / 2×quat→Mat3 / 锚点世界位置 | **40.2%** | **41.0%** |
| **点循环**：warm 匹配 + 锚点几何 + 有效质量 + 速度/rhs | **59.8%** | **59.0%** |
| 每次构建（均摊） | 429 ns/流形 | 406 ns/流形 |

（10k、8 线程、120 tick；429 ns × 34,168 流形 × 4 子步 ≈ 58.6 ms/tick，对上 `build_us` 的 ~93%。）

**点循环内部**：warm 匹配用消融测（临时短路 `match_warm_point`，点循环 **100 → 97 ns/点**）
⇒ 匹配只占 **~3%**；剩下 ~57% 是锚点几何 + 有效质量 + 速度/rhs 的纯浮点。

⚠️ **两条方法边界（下轮别再踩）**：

1. **纳秒级逐段拆不开**：单点一段 ~40 ns，而 `Instant` 在本机分辨率 **~100 ns** ⇒ 逐段读钟只能读到
   11 ns/点（占 7%），其余被量化吃掉。要更细必须换方法（采样剖析 / 计数 / 两遍结构化）。
2. **消融只对"关掉后物理仍大致成立"的部件可用**：短接 `match_warm_point` 可以（接触集 104k→113k）；
   把 `contact_masses` 换成常数会让 10k 场景直接发散（样本点 3.5M → 0.21M）⇒ 那个数不能信。

**判读**：

1. 点循环里**没有单点热点**（匹配 3%），是纯浮点 ⇒ 省它的办法是**减少点数/子步、向量化、上卡**。
2. **预处理那 ~40% 反而更可疑**：它是**每流形一次**（34k 次/子步），其中 `warm_index`
   （`HashMap<(u32,u32,u32),u32>`，默认 SipHash）每流形一次 ⇒ 下一步最值得单点替换的候选
   （直接映射表 / 把槽号从窄相带过来）。

## 3.13 实测：warm 槽 HashMap → 开放寻址表——**壁钟无收益（−0.3%，噪声内）**

§3.12 里预处理 ~40% 的最可疑单点是"每流形一次 `warm_index` 的 `HashMap`(SipHash) 查找"。
做了一个**语义等价**（不丢条目 ⇒ 物理逐位不变）的开放寻址 + 线性探测平表（键 = 3×u32、乘法混合哈希），
A/B 对照（同一场景、交错跑）：

| | 预处理段占比（探针开） | 每次构建（探针开） | 壁钟（探针关，4×3、120 tick、3 轮交错） |
|---|---|---|---|
| A：`HashMap` | 39.0–39.1% | 417–421 ns | 150.3 / 150.4 / 150.5 ms |
| B：开放寻址表 | 36.6–36.7% | 400–401 ns | 149.6 / 149.8 / 150.2 ms |

⇒ 探针开时构建降 **4.5%**、预处理段降 ~10%（约 17 ns/流形），但**壁钟只降 ~0.3%，落在噪声内**；
8×1 的 A/B 两组读数甚至互相矛盾（±5% 热漂移盖过差异）。**结论：查表成本被乱序执行掩盖，换表不值**
⇒ **已撤回**（不留 110 行无收益的复杂度）。

**等价性先验过**：换表后金样冻结基线 `pile5 600 16 0.01 4 3.0 30 4` **PASS** 且读数逐项相同
（入睡 2000/2000、超阈 0/0/0、Δpos max 0.0044）——所以"无收益"不是"改了物理才看起来没变"。

⚠️ **为什么不用有损"直接映射"**：34k 条目放进 4× 表（131k 格）按生日碰撞估计仍会丢 ≈4 千条（≈12%）
⇒ warm 缓存静默失效 ⇒ 物理改变、冻结基线作废。要用它必须先决定"接受行为变化并重录基线"，
那是产品决定，不是实现细节。

**下一步**：预处理那 40% 的下一嫌疑不是查表，而是 `material_pair` / `friction_frame` / `tangent_setup` /
两次 `quat→Mat3` / 锚点世界位置——都是每流形一次的纯算术 + `BodySet` 读取。

## 3.14 实测：预处理逐项拆——`material_pair` / `friction_frame` 各 ~5%，都不是杠杆

方法：`seg_time!` 宏在 `ISLAND_SEG_PROBE` 下对**单个阶段**计时（抽样 1/16 流形）；为压低插桩自身
开销，`material_pair` 与 `friction_frame` 各做一次"只计一个"的运行（其余段不计时），两档读数一致。

| 阶段 | ns/流形 | 占构建（未插桩 ≈420 ns） |
|---|---|---|
| **`material_pair`**（材质对 + Stribeck 判定） | **≈22** | **≈5%** |
| **`friction_frame`**（各向异性切向基） | **≈22** | **≈5%** |
| 锚点世界位置（≤4 点 × 2 次旋转 + 平均） | ≈61–75 | ≈11–14% |
| 点循环（§3.12） | — | ≈65%（未插桩） |
| 其余：入口 / warm 槽查找 / 2×quat→Mat3 / `out.push` | — | 五路同计时档下 36–37%（含计时与 TLS 开销） |

⚠️ **五路同时计时会把 total 从 ~420 抬到 ~600 ns**（每流形 10 次读钟 + TLS 记账）⇒ 只有**同一行内**
的占比可比；`material_pair` / `friction_frame` 的**绝对量在三种插桩档下都稳定在 ~22 ns**，可信。

**判读**：

1. 两个目标函数合计 **≈10% 构建 ≈ 4% solve ≈ 3% tick** ⇒ **不是杠杆，别再优化它们**。
2. 剩下的只有两块：**点循环 65%**（§3.12：纯浮点，无单点热点）与 **锚点世界 11–14%**
   （每流形 ≤4 点各 2 次 `mul_vec3` + 平均）。前者要动只能靠向量化/上卡/减点数；
   后者本来就是"按当前位姿重建"，没有可复用的部分。
3. 结论：构建这一层已经被拆到**没有廉价的大块**了。剩下的性能空间在
   **求解迭代（22–39%）的并行**与**减少接触点/子步**，或者换硬件路径。

## 3.17 实测：GPU 接触扫描吞吐（`PLAN-gpu §17.2` 第三片的前置）

新增 `crates/vxl-phys-gpu/examples/gpu_solve_probe`：**Jacobi 两趟**（每接触算增量 → 每体按 CSR 升序累加，
确定性），主机侧同式同序参考；本机 **RTX 4060 Ti / 8 GB**（Vulkan）。

| 项 | 读数 |
|---|---|
| 规模 | 100,000 接触 / 10,000 体（= M1 10k 堆一个子步的量级） |
| CPU 单线程（同式 Jacobi） | **4,243 µs/扫** |
| GPU（两核 + 提交 + 同步） | **133–179 µs/扫** ⇒ **24–32×** |
| 12 扫/帧 | CPU ≈ 50 ms → GPU ≈ **1.6–2.1 ms** |
| 口径 B：`max|Δv|`（GPU vs CPU） | **3.35e-8**（f32 精度内 ⇒ 移植忠实） |
| setup（含预热） | 0.9–1.0 ms |

**判据（预先钉死）**：≤1.0 ms/扫才继续 ⇒ **✅ 通过**（0.13–0.18 ms/扫）。

⚠️ **Amdahl：只搬迭代只有 ~28%**。M1 的 4×3 解算 120 ms = 构建 ~64 + 热启动 ~9 + 迭代 ~47；
把迭代换成 GPU（1.6 ms）再加每 tick 接触表回传（5.9 MB × 4 子步 ≈ 24 MB，PCIe ~10 GB/s ≈ 2.4 ms）：
`64 + 9 + 2 + 2.4 ≈ 77 ms` ⇒ tick 151 → **~108 ms（−28%）**，离 33 ms 仍差 3.3×。
⇒ **要拿性能档必须把构建也搬上卡**（状态常驻，§17.10 的方向），迭代上卡只是必要条件不是充分条件。

**边界**：本探针**不主张质量**——Jacobi 与默认档的顺序冲量不是一回事（收敛特性、摩擦锥、warm start 都不同），
且世界逆惯量用了对角近似。接进 `World` 必须走 §17.3 铁律：**显式档、默认档一行不走、判据是新档自己的
能量/落位口径**（不与主机档比逐位）。

## 3.18 实测：接触图着色深度——CPU 侧 SoA+SIMD 的天花板 ≈20%（且要新档）

「粗粒度 SoA 重构」在**单岛顺序 GS** 下没有向量化目标（GS 的顺序 = 约束序，天然串行）。
CPU 上唯一的并行形态是**按色分批的并行 GS**（同色约束不共享体 ⇒ 色内可并行且确定）。
先量着色深度（`contact_coloring_probe`，贪心边着色，`m1pile 25×20²`）：

| tick | 流形 | 色数 | 每色 均 / 最宽 |
|---|---|---|---|
| 20（沉降密集期） | 39,248 | **400** | 98 / 4,999 |
| 40 | 38,878 | **26** | 1,495 / 4,985 |
| 120（已基本入睡） | 1,728 | 14 | 123 / 280 |

⚠️ 色数对**贪心次序**很敏感（20 tick 的 400 色 vs 40 tick 的 26 色，同样的图规模）⇒ 真要做还得先解决着色质量。

**判读**：

1. 色内并行上限 = SIMD 宽度（4–8），而色数 ≥ 迭代数 ⇒ CPU 侧的理论增益 ≈ `SIMD/色数比`，
   折进 §3.11 的份额（迭代 22–39% of solve）后 **端到端 ≤20%**，且彩色 GS 与顺序 GS **收敛不同**
   （**必须新档**、不能比逐位）⇒ 性价比低于 GPU 路线（同一段 24–32×、且不需要着色）。
2. ⇒ **CPU 的 SoA+SIMD 不做**。SoA 的真正用处在 GPU（§3.17 探针用的就是扁平静态布局）。
   CPU 侧若要继续，只剩"减少接触点/子步"；性能档要靠 GPU 全链路（状态常驻）。

## 3.19 实测：构建内核上卡——0.85–1.12 ms/tick（B 的成本账闭合）

`crates/vxl-phys-gpu/examples/gpu_build_probe`：`make_iw`（每体 `M = R·diag·Rᵀ`）+ `build`
（每接触 `ra/rb` 与 `kn/kt1/kt2/kcross`，与 `helpers::contact_mass*` 同式），100k 接触 / 10k 体：

| 段 | 读数（RTX 4060 Ti） |
|---|---|
| `make_iw` | 79–104 µs |
| `build` | 133–176 µs |
| **× 4 子步** | **0.85–1.12 ms/tick**（CPU 同段 ~64 ms） |

**一致性（口径 B，逐列）**：`ra/rb` **逐位相同**；`kn/kt1/kt2` ≤ **6e-7** 绝对；交叉项 `kc` **1.7e-4**
绝对——两张世界逆惯量矩阵本身差 **1.4e-6**（WGSL 与 `Mat3::world_inv_inertia` 的运算序不同），
在"两向量内积之差"的缩并里被放大；属**缩并噪声**、不是公式错。

⇒ **B（全链路常驻）的成本账闭合**：构建 ~1 + 求解 1.6–2.1 + 窄/宽/积分（已有卡上档）⇒ 整 tick **几 ms**，
对 33 ms 有 8–10× 余量。**性能侧不再是问题，剩下全是质量与确定性**（见 `PLAN-gpu §30.3`）。

## 3.20 实测：端到端（B1+B3+B4）真实场景——1.4–1.7 ms/tick，口径 B 7.6e-5

`crates/vxl-phys-gpu/examples/gpu_resident_probe`：m1pile @40 tick 快照（**10,001 体 / 38,878 流形**）→
卡上**一条链一次提交**：`make_iw`（每体世界逆惯量）→ `build`（每接触 ra/rb + 4 个有效质量项）→
12×(`contact_sweep` + `body_apply`)；主机侧同式同序 Jacobi 作参考。

| 项 | 读数 |
|---|---|
| 全量上传（体表 + 接触表 = 1.8 MB） | **1.6–1.9 ms** |
| 主机参考（同式构建 + 12 扫 Jacobi，单线程） | 13.7 ms/子步 ⇒ 54.8 ms/tick |
| **卡上全链（一次提交 + 一次同步）** | **0.36–0.42 ms/子步 ⇒ 1.4–1.7 ms/tick** |
| 一致性 | 构建产物 `max|Δ|` 2.4e-2（相对 ~2e-5）；末态 **`max|Δv|` 7.6e-5** |

⇒ 对引擎现行的 151 ms/tick：**构建+求解这条链换成卡上后约 1.5 ms**（窄相/宽相/积分另有已上卡档）。
余量 **~20×**。⇒ **B 的性能侧确认**。

**下一片的两个明确任务**：
1. **B1 增量上传**：全量 1.8 ms 已与计算（1.5 ms）同量级 ⇒ 必须只传变动体（§17.10 已验证 2.7× 的上传项），
   否则每 tick 白付一倍。
2. **B2 窄相常驻**：去掉主机全量打包/解码（§17.10 记的那 ~0.35 ms 主机侧开销）。

**边界**：本读数用 Jacobi，**不等于**默认档顺序 GS 的质量（塔沉降/休眠未验）⇒ B6 必须带发散判据。

## 3.21 实测：B1 差量上传——2,500 体 117 KB = 150 µs（全量 1.5 ms），**同步后逐字节相同**

在同一探针里加 `scatter_records`：两次小 `write_buffer`（体号位模式数组 + 记录数组）+ 一个散写核，
把变动体写进常驻体表。判据按 `PLAN-gpu §30.2` B1：**增量同步后卡上体表与主机逐字节相同**。

| 项 | 读数 |
|---|---|
| 全量上传（10k 体 + 38.9k 接触 = 1,796 KB） | 1,537 µs |
| **差量上传（2,500 体 = 117 KB）** | **150 µs（10.2×）** |
| 同步后卡上 vs 主机体表 | **max|Δ| = 0（逐字节相同）** ✅ |

⚠️ 150 µs 里有一块是**固定地板**：`write_buffer` 的代价按**调用次数**算（§17.10 实测过），
本档 2 次调用 ≈ 60–90 µs ⇒ 差量再小也不会低于这个量级；要把地板也压掉得把"索引+记录"并成**一次**上传
（同一块缓冲里先索引后记录）。

⇒ B1 达标：每 tick 只传变动体后，上传从 1.5 ms 降到 ~0.15 ms（与卡上计算 1.4 ms 同量级但可接受），
下一步 B2（窄相常驻去主机打包）。

## 3.22 实测：窄相卡上档的"主机侧 0.35 ms"其实**不是主机侧**——是同步往返

`gpu_narrow_tier_probe`（World 级，两链只差"谁跑窄相"，240 tick、8 线程）自带分项账：

| 每趟均值（常驻已生效） | 小档 | m1 档 |
|---|---|---|
| 打包（`pack_bodies`） | 0.001 | 0.001 |
| 比对（逐记录 diff） | 0.001 | 0.001 |
| 上传（2 次 `write_buffer`） | 0.005 | 0.007 |
| **后端（写+派发+回读+解码）** | **0.171** | **0.188** |
| 回填 + 装配 | 0.001 | 0.001 |
| **合计** | **0.180 ms** | **0.198 ms** |

卡上档内部分项（同一趟）：**"提交 + 映射 + 等" 0.165 / 0.181 ms**（占后端 96%），
其余（变动打包 0.000、上传写 0.005/0.006、参数+对表 0.001、编码 0.001、解码 0.002、摊平 0.000）都可忽略。

⇒ **`PLAN-gpu §17.10` 说的"多出来的 ~0.35 ms 全在主机侧（全量重打包/回读解码/回填装配）"在常驻档下已不成立**：
- 主机侧三项合计 **~0.010 ms（5%）**；
- 真正的成本是**每趟一次同步往返**（`submit` → `poll(Wait)` → `map_async`），0.17–0.19 ms；
- 4 子步/帧 ⇒ 仅往返就 ~0.7 ms/tick，且**与数据量基本无关**（小档与 m1 档差 3%）。

**判读（改计划）**：
1. **B2「窄相常驻去主机打包」作废**——主机打包已经只有 1 µs，删它没有收益。
2. 该做的是 **B5：把窄相、构建、求解并进同一次提交**，一个 tick 只等一次（往返从 4 次降到 1 次）；
   端到端探针（§3.20）已经是"一次提交"，1.4–1.7 ms/tick 里**不含**这段往返——这正是它比 World 路径快一个档的原因。
3. 若还要再压，只能上"卡端编排"（多 pass 常驻、主机不每帧等结果）——那是 B 的最后形态。

## 3.23 基线：M1 的 4 子步下卡上窄相档到底几次往返、贵在哪

新探针 `gpu_roundtrip_baseline`（m1pile 25×20²、**4 子步**、8 线程、120 tick；两条链只差"谁跑窄相"）：

| 项 | 读数（两次跑，机器漂移范围内） |
|---|---|
| 窄相趟数 | **4.0 趟/tick**（480 趟 / 120 tick）——每子步都检测 ⇒ 每趟一次同步 |
| 每趟候选对 | **55,331 对**（宽相对数，远大于流形数） |
| 每趟分项 | 打包 0.055 · 比对 0.043 · 上传 0.33–0.45 · **后端 11.8–17.5** · 回填+装配 0.48–0.49 ms |
| 后端内 | 写 0.31–0.43 · 参数+对表 0.50–0.68 · 编码 0.004 · **提交+映射+等 8.5–14.0** · 解码 1.27–1.36 |
| **往返合计** | **34–56 ms/tick**（占卡上窄相 **66–75%**） |
| 卡上窄相 vs 默认 CPU | **4.8–8.4× 更慢**（51–75 ms/tick vs 8.9–10.8） |

⚠️ **"提交+映射+等"里含 GPU 执行本身**：55k 对 ÷ 8.5–14 ms ≈ **155–254 ns/对**，
而 CPU 8 线程窄相是 8.9 ms/4 趟 ÷ 55k ≈ **40 ns/对** ⇒ **卡上窄相单对慢 4–6×**。
⇒ 把 4 次提交并成 1 次（B5）只能省掉**提交地板**（约 0.2 ms/趟），**省不下这 34–56 ms**；
**真正的瓶颈是窄相内核本身的吞吐**，不是往返次数。

**⚠️ 探针坑（自己踩的，也是这轮之前 2.07 趟的来源）**：`NarrowTier::new` 的容量要按**宽相对数**给。
我先给 `cap_p = 65,536` ⇒ m1 的 55k 对经常超容量 ⇒ `narrow_run` 返回 `Err` ⇒**整趟静默回退 CPU**
（`calls` 不增，看起来像"只跑了 2 趟"）。给 `400,000` 后才是 4.0 趟/tick。**任何"趟数不对"先查容量。**

**判读（对 B 的影响）**：
1. B2/B5 若按原计划"把窄相搬上卡 + 少等待"，**收益为负**（当前窄相卡上档已比 CPU 慢 5–8×）；
2. B 的窄相要么**改写内核**（GPU 友好：按体对批处理的 SIMD 风格，而不是现在的分族 SAT），
   要么**保留 CPU 窄相**（8 线程 40 ns/对已很快）而只把构建+求解放卡上——
   后者与 §3.20 的端到端（1.4–1.7 ms/tick）拼起来仍远好于 33 ms 目标。
